# 프로젝트 전체 기획서 kind

이 파일의 kind는 프로젝트 차원의 의사결정과 문서 간 계약만 소유한다. 상세 시스템·수치·화면 명세는 해당 kind로 넘기며 통합 문서에 복제하지 않는다.

| 기획서 / kind ID / profile | 목적·주 독자 | 반드시 답할 결정 | 필수 산출물 | 기본 제외 | 인접 문서 핸드오프 | 완료 조건 |
|---|---|---|---|---|---|---|
| 게임 제안서<br>`game-proposal`<span id="game-proposal"></span><br>`concept` | 최초 소개와 착수 판단<br>경영진, 퍼블리셔, 투자·제작 책임자 | 무엇을 누구에게 왜 제공하며, 핵심 재미와 차별점은 무엇인가? 예상 범위·일정·위험은 수용 가능한가? | 원페이지 피치, 장르·플랫폼·타깃, 핵심 재미 기둥, 차별점, 고수준 일정·리스크 | 상세 규칙, 화면 명세, 밸런스 수치, 작업별 일정 | 입력: `game-concept` 초안<br>출력: `game-concept`, `development-plan`, `master-gdd` | 의사결정자가 진행·보류·폐기 중 하나를 근거와 함께 선택할 수 있다 |
| 게임 콘셉트 기획서<br>`game-concept`<span id="game-concept"></span><br>`concept` | 방향성·분위기·경험 정렬<br>디렉터, 기획·아트·내러티브 리드 | 플레이어가 어떤 감정과 행동을 반복하는가? 세계·톤·비주얼 키워드와 금지선은 무엇인가? | 경험 문장, 콘셉트 키워드, 코어 루프, 세계·톤 요약, 비주얼 방향, 범위 경계 | 상세 시스템 규칙, 제작 일정, 데이터 스키마, 최종 아트 | 입력: `game-proposal`<br>출력: `master-gdd`, `world-bible`, `ui-spec`, 각 시스템 kind | 각 직군이 동일한 경험 목표와 범위 경계를 설명할 수 있다 |
| 게임 디자인 문서·GDD<br>`master-gdd`<span id="master-gdd"></span><br>`full` | 전체 구조와 모듈 간 계약 통합<br>전 개발 조직, 외부 공동개발사 | 어떤 문서가 어떤 결정을 소유하며 시스템·콘텐츠·UI·데이터가 어디서 연결되는가? | 코어 루프, 기능·문서 지도, 모듈 의존성, 공통 용어, 인터페이스·핸드오프 매트릭스, 결정·가정 로그 | 하위 kind의 상세 표·수치·와이어프레임 복제 | 입력: 모든 승인 kind<br>출력: `development-plan`, `data-table-spec`, `logging-spec` 및 영향받는 kind | 모든 핵심 기능에 단일 소유 kind와 추적 가능한 계약 링크가 있고 충돌·고아 기능이 없다 |
| 개발 일정 기획서<br>`development-plan`<span id="development-plan"></span><br>`production` | 개발 단계·책임·완료 기준 관리<br>프로듀서, PM, 파트 리드 | 언제 무엇을 누가 어떤 우선순위와 의존성으로 완료하는가? 각 게이트의 승인 조건은 무엇인가? | 마일스톤, WBS·백로그 묶음, 담당·RACI, 우선순위, 의존성, 리스크 버퍼, 게이트별 완료 조건 | 게임 규칙, 밸런스 설계, UI 배치, 마케팅 문안 | 입력: `game-proposal`, `master-gdd`, 각 kind의 작업 추정<br>출력: `update-spec`, 각 구현 담당 kind | 담당자·선후관계·날짜·검수자가 없는 작업이 없고 마일스톤 경로를 계산할 수 있다 |
