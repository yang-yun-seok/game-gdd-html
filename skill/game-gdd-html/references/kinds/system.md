# 시스템 기획서 kind

이 영역은 플레이어가 경험하는 지속 상태와 게임 규칙을 소유한다. 화면 배치, 최종 밸런스 값, 기획 데이터 항목·로그 이벤트 정의는 각각 전용 kind로 넘긴다. 클라이언트·서버 분담, 저장 방식, 트랜잭션 같은 구현 선택은 결과·보존·복구 기준을 충족하기 위한 `개발 협의 조건`으로 남긴다.

| 기획서 / kind ID / profile | 목적·주 독자 | 반드시 답할 결정 | 필수 산출물 | 기본 제외 | 인접 문서 핸드오프 | 완료 조건 |
|---|---|---|---|---|---|---|
| 캐릭터 시스템 기획서<br>`character-system`<span id="character-system"></span><br>`system` | 캐릭터 상태·성장 구조 정의<br>시스템·전투·데이터·UI·QA 기획 및 개발 협업 담당 | 능력치, 레벨, 직업, 스킬 슬롯과 성장 상태는 어떤 조건에서 생성·변경되며 재진입 시 무엇이 유지·복원되는가? | 상태 모델, 능력치 정의, 성장·전직 규칙, 스킬 소유 구조, 초기화·복구 규칙 | 전투 조작·역할, 최종 성장 곡선, 화면 배치 | 입력: `game-concept`<br>출력: `character-combat`, `progression-balance`, `data-table-spec`, `ui-spec` | 모든 상태 변화에 조건·결과·유지·복원 기준·예외가 정의되며 구현 방식은 개발 협의 조건으로 분리된다 |
| 아이템 시스템 기획서<br>`item-system`<span id="item-system"></span><br>`system` | 아이템 분류와 생명주기 정의<br>시스템·콘텐츠·데이터·UI·QA 기획 및 개발 협업 담당 | 아이템은 어떤 조건에서 획득·중첩·장착·사용·이동·폐기되며 결과가 어떻게 보이는가? | 분류·등급 체계, 인벤토리 규칙, 획득·사용·장착 상태 흐름, 귀속·만료·소실 규칙 | 상점 가격, 보상량·드롭률, 화면 레이아웃 | 입력: `game-concept`<br>출력: `reward-design`, `store-product`, `data-table-spec`, `ui-spec`, `exception-spec` | 각 아이템 유형의 허용 행위, 기준 상태, 성공·실패 결과가 모호하지 않고 처리 위치는 개발 협의 조건으로 남는다 |
| 퀘스트 시스템 기획서<br>`quest-system`<span id="quest-system"></span><br>`system` | 퀘스트 수명주기와 판정 정의<br>시스템·콘텐츠·내러티브·UI·QA 기획 및 개발 협업 담당 | 수락·진행·공유·완료·실패·포기·재도전은 어떤 조건과 우선순위로 판정되는가? | 상태도, 목표 유형, 진행 카운트 규칙, 선후행·반복 조건, 보상 지급 조건·반복 수령 결과 | 스토리 대사, 보상 수치, 화면 배치 | 입력: `scenario-design`<br>출력: `reward-design`, `ui-spec`, `logging-spec`, `exception-spec` | 정상·중단·동시 진행 경로마다 재현 가능한 상태·보상·피드백 결과가 있다 |
| 업적 시스템 기획서<br>`achievement-system`<span id="achievement-system"></span><br>`system` | 장기 목표의 추적·달성·수령 규칙 정의<br>시스템·콘텐츠·데이터·UI·QA 기획 및 개발 협업 담당 | 조건은 누적·단계·비공개·반복 중 무엇이며 달성과 보상 수령은 어떻게 분리되는가? | 조건 유형, 단계·진행 모델, 공개 정책, 달성·수령 상태도, 소급 적용 규칙 | 보상량, 배지 시각 디자인, 이벤트 KPI | 입력: `game-concept`<br>출력: `reward-design`, `ui-spec`, `logging-spec`, `data-table-spec` | 각 조건이 단일한 판정 기준과 테스트 가능한 완료·수령 결과를 가진다 |
| 제작·강화 시스템 기획서<br>`crafting-enhancement-system`<span id="crafting-enhancement-system"></span><br>`system` | 재료 소비와 제작·강화 상태 전이 정의<br>시스템·경제·밸런스·UI·QA 기획 및 개발 협업 담당 | 재료·비용은 어느 결과 시점에 소비된 것으로 보며 성공·실패·보호·복구·반복 실행의 상태는 어떻게 달라지는가? | 레시피·강화 규칙, 자원 차감→결과→피드백 순서, 성공·실패 상태도, 재료 부족·중단·반복 요청 예외, 확률 파라미터 계약 | 확률·비용 최종 튜닝, 경제 총량, 화면 배치 | 입력: `item-system`<br>출력: `random-probability-system`, `game-economy`, `ui-spec`, `data-table-spec`, `logging-spec` | 자원 총량 변화와 반복 요청 결과가 규칙에 부합하고 모든 성공·실패 분기가 QA 가능하며 보장 방식은 개발 협의 조건으로 남는다 |
| 매칭 시스템 기획서<br>`matchmaking-system`<span id="matchmaking-system"></span><br>`system` | 대기 그룹 구성과 상대 탐색 규칙 정의<br>시스템·전투·라이브·UI·QA 기획 및 개발 협업 담당 | 실력·지역·플랫폼·파티·대기 시간을 어떤 우선순위로 완화하며 후보가 없을 때 어떤 결과를 제공하는가? | 후보 풀·대기 그룹 모델, 매칭 점수·탐색 범위, 완화 타임라인, 파티·재접속 규칙, 취소·타임아웃·봇 대체 정책 | 전투 승패 규칙, MMR 수치 튜닝, 대기 화면 배치 | 입력: `combat-system`<br>출력: `ux-flow`, `logging-spec`, `exception-spec`, `combat-balance` | 동일 조건에서 허용 후보, 거절 사유, 대기 변화와 종료 결과를 판정할 수 있고 대기열 구현은 개발 협의 조건으로 남는다 |
