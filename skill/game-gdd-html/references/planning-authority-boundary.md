# 기획 권한 경계

이 스킬은 **게임 기획 결과**를 확정한다. 소프트웨어 구현 설계는 확정하지 않는다.

## 문서 첫머리

생성물 표지에는 계약의 한국어 문서명을 한 번만 표시한다. canonical kind/profile ID는
`gdd-kind`, `gdd-profile` HTML 메타데이터에만 둔다.

```text
<한국어 문서명>
```

`document.subtitle`에는 대상 기능과 문서 목적만 쓴다. 문서명, kind/profile ID, 내부 생성
과정을 반복하지 않는다. 최종 전달의 첫 문장은 `문서 종류: <한국어 문서명>`으로 시작한다.

## 기획이 확정하는 것

- **무엇**을 제공하는가: 기능, 콘텐츠, 화면, 규칙의 대상과 범위
- **왜** 필요한가: 목표 경험, 문제, 사업·운영 목적
- **플레이어가 관찰할 결과**: 입력·선택 뒤 보이는 상태, 피드백, 보상, 실패·복구 결과
- **게임 규칙**: 조건, 우선순위, 계산 의미, 상태 전이, 예외, 한도
- **수용조건**: 승인·플레이테스트·QA에서 관찰하거나 측정할 완료 기준

규칙의 `처리`는 게임 도메인의 판정 순서와 결과를 뜻한다. 코드 실행 순서나 알고리즘을 뜻하지 않는다.

## 기획이 확정하지 않는 것

다음은 문서 본문·표·다이어그램·예시에서 구현안으로 확정하지 않는다.

- 클래스, 메서드, 모듈, 패키지
- API, endpoint, request/response DTO, protocol
- DB·테이블의 물리 구조, 인덱스, 저장 엔진, 쿼리
- 서버·클라이언트 책임 분할, 서비스·프로세스·스레드 구조
- 알고리즘, 실행 가능한 의사코드, 자료구조
- 트랜잭션 경계, lock, queue, rollback 구현
- idempotency key, UUID 형식·생성 방식
- SQL·언어별 데이터 물리 타입
- 프레임워크, 라이브러리, 클라우드 제품
- tick rate, frame loop, 동기화·복제 방식

사용자가 기술을 명시했으면 `사용자 제공 기술 제약 · 개발 확인 필요`로 인용할 수 있지만,
기획 판단으로 확대하거나 대안을 선택하지 않는다.

## 기술중립적 품질조건과 개발 협의

구현 대신 관찰 가능한 품질조건을 쓴다.

- “결과 화면은 확인 행동 뒤 목표 시간 안에 표시된다.”
- “반복 입력·재시도에도 플레이어가 받는 보상은 한 번이다.”
- “재접속 뒤 승인된 진행·재화 결과가 플레이어에게 일관되게 보인다.”
- “지원 입력 장치에서 같은 필수 행동에 도달할 수 있다.”

구현 판단이 필요하면 다음만 `개발 협의`로 남긴다.

| 항목 | 내용 |
|---|---|
| 기획 요구 | 무엇과 플레이어 관찰 결과 |
| 품질조건 | 측정 가능한 목표·실패 기준 |
| 제약 | 플랫폼, 보안, 운영, 일정 등 알려진 조건 |
| 개발 결정 필요 | 구현팀이 선택해야 할 쟁점이며 해법은 확정하지 않음 |
| 담당·시점 | 결정 책임자와 필요한 마일스톤 |

권한 경계 문구를 표지와 각 섹션에 반복하지 않는다. 실제 구현 판단이 필요한 항목만
`개발 협의`로 모은다.

## 기술 협업 kind 경계

| kind | 허용 | 금지 |
|---|---|---|
| `data-table-spec` | 논리 엔터티·필드 의미, 단위, 허용 범위, 필수 여부, 관계, 검증 규칙, 예시값 | DB 물리 테이블·컬럼 배치, SQL 타입, PK·인덱스, 저장·마이그레이션 구현, UUID 방식 |
| `logging-spec` | 이벤트 의미·이름, 발생 조건·시점, 행위자·맥락·결과의 논리 속성, 분석 질문, 개인정보 최소화 조건 | SDK·API, 전송 프로토콜, queue·pipeline·warehouse 구조, 물리 타입, UUID·세션 생성 방식 |
| `logic-rule-spec` | 전제조건, 선언형 조건·결과, 우선순위, 결정표, 상태 전이, 게임 공식, 경계·수용 사례 | 클래스·메서드, 실행 가능한 의사코드, 알고리즘·자료구조, API, 서버·클라이언트 분할 |
| `exception-spec` | 예외 발생 조건, 플레이어 피드백, 보존돼야 할 게임 결과, 보상·재시도·재진입 규칙, 운영 에스컬레이션 | 트랜잭션·rollback 구현, idempotency key, lock·queue, DB 복구, 네트워크 재시도 알고리즘 |

`Table ID`, `Rule ID`, `Event ID`, `Screen ID` 같은 논리 참조 ID는 사용할 수 있다.
형식·생성·저장 방식은 `개발 협의`다.

## 검토와 수리

구현 방식이 발견되면 다음 중 하나로 수리한다.

1. 플레이어 관찰 결과나 기술중립적 수용조건으로 바꾼다.
2. 필요한 기술 판단만 `개발 협의`로 이동한다.
3. 문서 목적과 무관하면 삭제한다.

구현 방식이 하나라도 기획 확정처럼 남으면 의미 검토를 통과시키지 않는다.
