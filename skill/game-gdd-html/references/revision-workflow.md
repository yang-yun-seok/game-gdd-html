# 기존 기획서 수정

기존 문서의 부분 변경·보완·수치 조정·모순 수정 요청에 사용한다. 사용자가 내용 심화를 요청하면 해당 범위의 결정을 구체화한다. 단순 오탈자·표현 수정에 전체 재기획을 적용하지 않는다.

## 1. 기준 원본 확보

사용자가 지정한 파일 또는 현재 작업의 연결 원본을 사용한다. 이름이 비슷한 파일만 보고 최신본으로 단정하지 않는다. 후보의 제목·버전·내용으로 해결되지 않는 모호함만 묻는다.

- 렌더러 JSON이 있으면 HTML과 내용·버전이 일치하는지 확인하고 JSON을 기준으로 삼는다.
- 이 버전으로 생성한 HTML은 편집용 JSON을 포함한다. 준비 도구가 손실 없이 추출하고 HTML이 이후 수동 변경되었는지도 확인한다.
- 오래된 HTML 또는 수동 변경된 HTML은 `needs-reconstruction`과 읽기용 근거 파일을 반환한다. 먼저 대응 JSON을 찾는다. 없으면 원본 전체를 읽고 표·도식·차트·출처·결정·미정 상태를 보존한 baseline JSON으로 복원한다. 근거 파일의 텍스트 추출만으로 복원이 끝났다고 판단하지 않는다.
- profile이 없는 이전 JSON도 `needs-reconstruction`으로 원본 데이터를 보존한다. 실제 제목·내용에서 문서 종류를 파악해 현재 메타데이터·섹션 구조에 대응시킨 baseline을 별도로 만든다. 형식 변환과 기획 결정 변경을 구분하고 복원 전후 내용이 일치하는지 확인한다.
- Markdown·PDF·Word는 해당 읽기 도구로 내용을 확보하고 같은 방법으로 baseline JSON을 만든다. 표·그림을 읽을 수 없으면 해당 부분의 불확실성을 밝히고 확인 가능한 수정부터 수행한다.
- 복원 문서는 원본과 내용 대조 후 렌더·검증한다. 이때 불명확한 문장을 임의로 새 결정으로 바꾸지 않는다. 복원 한계가 있으면 전달한다.

```bash
python "$SKILL_DIR/scripts/revise_gdd.py" prepare \
  --source existing.html --request-file working/change-request.txt \
  --output-dir working/revision
```

짧은 요청은 `--request "변경 요청"`을 사용해도 된다. 반환 manifest의 `baseline`, `candidate`, `context`를 읽는다. baseline과 사용자 원본은 수정하지 않는다. 모든 준비·비교 출력은 기존 파일과 이름이 겹치면 새 이름으로 저장된다.

## 2. 변경과 영향

수정 전에 `working/revision/change-plan.md`에 변경 위치·이유·직접 영향·간접 영향·유지할 결정을 짧게 적는다. 작은 문구 수정이면 몇 줄로 충분하다. 내부 계획을 사용자 본문에 넣지 않는다.

- 기존 profile·kind·scope·섹션 ID·논리 ID를 유지하며 candidate의 필요한 블록만 수정한다. 기본값이나 다른 문서의 수치로 기존 결정을 교체하지 않는다.
- 사용자 요청이 범위나 종류를 바꾸면 신규 요청 컴파일러로 필요한 계약을 확인한 후 기존 내용을 병합한다. 새 scaffold로 문서를 덮어쓰지 않는다.
- 수치·조건·명칭의 모든 사용처를 검색한다. 규칙표·계산 예시·도식·차트·UI 표시·QA·결정 로그의 의미가 같은지 대조한다. 단순 문자열 치환으로 끝내지 않는다.
- 예: 강화 비용이 100→150이면 3회 소비 300→450, 소지금 400의 가능 횟수 4→2, 부족 표시·QA 입력·차트 값까지 확인한다. 다른 재화나 무관한 '100'은 바꾸지 않는다.
- 관련 문서가 제공되면 실제 연결 ID를 추적한다. 사용자가 수정 대상으로 포함한 문서는 각각 baseline과 candidate를 만들고 수정한다. 포함하지 않은 문서는 영향만 보고한다. 미제공 문서는 문서명·필요 결정·영향을 검토 필요로 남긴다.
- 의미 있는 변경에는 버전과 수정일을 갱신한다. 날짜는 사용자 시간대를 따른다. 상태를 임의로 '확정'으로 올리지 않는다. 변경된 가정·미정의 상태를 드러낸다.

## 3. 비교·검토·출력

```bash
python "$SKILL_DIR/scripts/revise_gdd.py" compare \
  --manifest working/revision/revision-manifest.json \
  --output-dir working/revision
```

- `--manifest`에는 `prepare`가 반환한 `manifest` 경로를 쓴다. 비교 도구가 해당 작업의 기준본·후보본을 읽고 기준본의 JSON 내용이 준비 시점과 같은지 확인한다. 기준본이 바뀌면 원본에서 기준본을 복구하고 후보본을 보존한 채 다시 비교한다.
- 기존 `--baseline … --updated …` 명령도 준비 폴더에서 두 파일의 짝과 기준본을 확인한다. 예전 manifest에는 기준본 해시가 없어 준비할 때 기록한 원본 파일이 필요하다. 별도로 제공된 두 문서의 직접 비교에서는 `baseline_integrity`가 `standalone`으로 표시된다.
- `revision-diff.json`에는 JSON 경로별 전후 값, 변경 섹션, 계약 변경이 기록된다. 요청에 따른 변경과 파생 수정을 전부 설명할 수 있어야 한다. 의도하지 않은 삭제·재작성은 되돌린다.
- 좁은 수정에는 `--allow-section <section-id>`를 반복해 허용한 변경 섹션을 제한할 수 있다. 기존 섹션 사이의 순서가 바뀌면 이동한 섹션에도 같은 제한이 적용된다. 필요한 파생 수정은 사유를 기록한 후 목록에 포함한다. 메타데이터·출처 등 섹션 밖 변경도 diff에서 따로 검토한다.
- 계약·섹션 구성 변경은 기본적으로 `blocked`다. 사용자 요청에 해당 변경이 있을 때만 `--allow-scope-change`로 비교한다. 이 옵션은 렌더러의 profile·kind·scope 검증을 우회하지 않는다.
- `needs-review`는 실제 차이가 있다는 뜻이다. 자동 비교는 의미 충돌, 수식 타당성, 연계 문서 일관성을 판정하지 않는다.
- `design-depth.md`의 `review` 기준으로 변경 부분과 연결 부분을 검토한다. 사용자 요청 충족, 기존 결정 보존, 계산 일치, 예외·수용조건 갱신의 실제 근거 경로를 기록한다. 미해결 모순은 수정하고 핵심 미정은 영향과 함께 표시한다.
- 새 버전 HTML을 렌더하고 기존 자동 검증 및 브라우저 검수를 수행한다. PDF는 요청된 경우만 생성한다. 의미 검토와 자동 구조 검증 결과를 구분해 전달한다.

최종 전달에는 문서 종류, 새 HTML 링크, 주요 변경, 연계 영향, 남은 결정만 간결하게 포함한다. 원본 JSON·내부 비교 보고서는 사용자가 요청할 때 제공한다.
