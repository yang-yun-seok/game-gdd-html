# 품질 체크리스트

## 1. 문서 영역과 범위

- [ ] 생성물 표지에 한국어 문서 종류 `<label>`이 한 번만 표시되고, canonical kind/profile ID는 HTML 메타데이터에만 있다.
- [ ] `document.subtitle`은 대상 기능과 문서 목적만 설명하며 문서명·canonical 코드·profile·생성 과정을 반복하지 않는다.
- [ ] 전달 메시지는 `문서 종류: <한국어 label>`로 시작하며 canonical 코드를 노출하지 않는다.
- [ ] 사용자 요청과 `document.profile`이 일치한다.
- [ ] 사용자가 명시하거나 라우터가 확정한 세부 문서 종류와 `document.kind`가 일치한다.
- [ ] kind 문서는 canonical kind ID를 사용하며, `document.kind`의 계약 profile과 `document.profile`이 일치한다.
- [ ] 사용자가 broad profile 일반 문서만 요청한 경우에는 `document.kind`를 억지로 만들지 않고 기존 profile 경로를 사용했다.
- [ ] `full`은 전체·통합·마스터 GDD를 명시적으로 요청했을 때만 선택했다.
- [ ] `development-plan`과 `update-spec`은 `production` 프로필을 사용한다.
- [ ] 문서 제목·표지에서 대상 기능과 용도가 명확하고 같은 문서명이 여러 라벨로 반복되지 않는다.
- [ ] `summary`는 HTML 메타 설명용 비가시 요약이며 별도 `프로젝트 브리프` 섹션·카드·본문 블록으로 출력되지 않는다.
- [ ] 선택 프로필의 표준 섹션만 본문에 사용했다.
- [ ] 다른 프로필의 상세를 복제하지 않고 내부 검토에서 소유 문서와 연결했다.
- [ ] `filter.selected_kinds`, `filter.documents`, `scope.document_plans`가 같은 문서 집합과 profile 매핑을 가진다.
- [ ] `filter.selected_generic_profiles`의 각 profile이 `kind: null` 문서 계획으로 보존된다.
- [ ] document plan마다 하나의 kind 또는 하나의 일반 profile만 들어 있다.
- [ ] 복수 kind 요청은 별도 HTML로 분리했다. 같은 profile의 kind도 하나의 문서로 합치지 않았다.
- [ ] kind 목록에 묶음 전달을 요청한 경우 본문을 합치지 않고 독립 HTML과 선택적 색인·패키지로 구성했다.
- [ ] 포함 범위와 제외 범위가 구분된다.
- [ ] `document.scope`가 `core + triggered + dependency`로 계산된 실제 작성 범위를 담는다.
- [ ] 패싯, 선택 섹션, 선택 이유가 1차 필터 결과와 일치한다.
- [ ] kind 문서의 `document.scope.facets`가 계약의 `default_facets`를 모두 포함한다.
- [ ] 포함·제외 충돌과 필수 의존성 누락이 없다.
- [ ] 확정, 가정, 제안, 검토 필요가 구분된다.
- [ ] 동일 용어와 ID가 문서 전체에서 일관된다.

## 2. 실무 문체

- [ ] 섹션은 배경 설명보다 결정 사항과 규칙을 먼저 제시한다.
- [ ] 문장은 짧은 선언형이며 한 문장에 조건 또는 규칙 하나만 담는다.
- [ ] 해당 항목의 조건·규칙·플레이어 결과·예외·UI 표시·검증 기준을 찾을 수 있다.
- [ ] `이 문서는`, `본 문서`, `제안한다`, `고려할 수 있다`가 관성적으로 반복되지 않는다.
- [ ] 요청 해석, 키워드 조합, 범위 필터, 섹션 선택 등 AI 생성 과정을 설명하지 않는다.
- [ ] GDDQL, profile·kind·category ID, facet, scope, selected section, required output, coverage, handoff의 내부 값이 표지·본문·목차·부록·결정 로그에 없다.
- [ ] `PILLAR 01`, `DESIGN`, `OWNED`, `REFERENCE`, `HANDOFF` 같은 불필요한 영문 대문자 태그가 없다.
- [ ] 표·카드·태그·담당명은 한국어를 우선하고 제품명·통용 약어 등 필요한 영문만 사용한다.
- [ ] 설명 문단은 규칙 판단에 필요한 이유와 제약만 남긴다.

## 3. 의사결정과 개발 전달 가능성

- [ ] [기획 깊이 기준](design-depth.md)에 따라 핵심 결정의 이유·대가, 정상·경계 사례, 수치 재계산, 관찰 가능한 수용조건을 실제 본문 경로로 검토했다.
- [ ] 기존 문서 수정은 [수정 절차](revision-workflow.md)에 따라 원본 보존, 전후 차이, 관련 표·도식·예시·QA의 일치와 연계 영향을 확인했다.

- [ ] 각 섹션이 답해야 할 결정과 완료 조건이 명확하다.
- [ ] 규칙이 필요한 항목에는 전제조건, 입력, 도메인 판정, 플레이어 관찰 결과, 실패가 있다.
- [ ] 흐름이 필요한 항목에는 시작, 성공, 취소·실패, 재진입이 있다.
- [ ] 상태가 필요한 항목에는 기본, 진행, 완료, 오류·예외가 있다.
- [ ] 수치가 필요한 항목에는 단위, 기본값, 범위, 공식 또는 조정 근거가 있다.
- [ ] 데이터가 필요한 항목에는 논리 의미, 단위·범위, 필수 여부, 관계, 게임 규칙상 가시성·변경 가능 주체 또는 검증 책임이 있다.
- [ ] QA 또는 승인 담당자가 확인할 수 있는 수용 조건이 있다.
- [ ] 다른 직군·문서에 필요한 입력과 출력은 내부 검토에서 추적된다.
- [ ] kind 계약의 모든 `required_outputs`가 현재 문서의 실질적 결과 또는 내부 참조로 추적된다.
- [ ] kind 계약의 `handoffs` 중 이번 범위에 필요한 항목에 대상, 입력, 필요한 결정, 완료 조건이 내부적으로 정리된다.
- [ ] 사용자가 문서 간 협업 표를 명시적으로 요청하지 않았다면 전용 협업 표를 만들지 않았다.
- [ ] 요청된 협업 표에는 한국어 문서명·필요 결정·전달 자료·완료 기준·담당만 있으며 canonical 코드와 내부 상태명이 없다.

### 공통 결과 내부 점검

다음 차원을 내용 복제로 채우지 않는다. 생성·검토 과정에서만 각 항목을 정확히 하나의
`owned`, `reference`, `N/A` 상태로 분류하고 대상 경로·참조 ID·사유를 확인한다.

- [ ] `planning-intent`
- [ ] `application-scope`
- [ ] `operating-rules`
- [ ] `schedule-and-ownership`
- [ ] `data-contract`
- [ ] `ui-touchpoints`
- [ ] `exception-policy`
- [ ] `telemetry-plan`
- [ ] `completion-criteria`

- [ ] `owned`인 차원은 현재 kind의 결정 범위와 완료 조건을 충족한다.
- [ ] `reference`인 차원은 실제 소유 kind와 안정적인 Rule/Screen/Table/Event/Milestone ID로 이동할 수 있다.
- [ ] `N/A`에는 검토 가능한 범위 사유가 있으며 편의상 누락한 항목이 아니다.
- [ ] 다른 kind가 소유한 일정, 데이터 컬럼, UI 화면, 예외 규칙, 로그 스키마를 현재 문서에 복제하지 않았다.
- [ ] 위 상태와 9개 차원을 나열한 전용 커버리지 표·부록을 렌더하지 않았다.

## 4. 기획 권한 경계

- [ ] 확정한 내용이 무엇·왜·플레이어가 관찰할 결과·게임 규칙·수용조건에 한정된다.
- [ ] 클래스·메서드·모듈·패키지를 기획 결정으로 지정하지 않았다.
- [ ] API·endpoint·DTO·protocol을 확정하지 않았다.
- [ ] DB 물리 구조·인덱스·저장 엔진·쿼리·데이터 물리 타입을 확정하지 않았다.
- [ ] 서버/클라이언트·서비스·프로세스·스레드 책임 구조를 확정하지 않았다.
- [ ] 알고리즘·자료구조·실행 가능한 의사코드를 확정하지 않았다.
- [ ] 트랜잭션·lock·queue·rollback 구현, 멱등 키, UUID 형식·생성 방식을 확정하지 않았다.
- [ ] 프레임워크·라이브러리·클라우드 제품·틱레이트·복제 방식을 확정하지 않았다.
- [ ] 기술 요구는 플레이어 관찰 결과와 측정 가능한 품질조건으로 표현했다.
- [ ] 구현 판단은 `개발 협의`에 기획 요구·품질조건·제약·개발 결정 필요·담당·시점만 적었으며 해법을 선택하지 않았다.
- [ ] 사용자 제공 구현안은 `사용자 제공 기술 제약 · 개발 확인 필요`로 구분했다.
- [ ] 기획·개발 권한 경계 설명을 표지와 본문에 반복하지 않고 실제로 필요한 `개발 협의`만 남겼다.

기술 협업 kind 조건:

- [ ] `data-table-spec`은 논리 필드 의미·단위·범위·필수 여부·관계·검증 규칙까지만 소유한다.
- [ ] `logging-spec`은 이벤트 의미·조건·시점·논리 속성·분석 질문까지만 소유한다.
- [ ] `logic-rule-spec`은 선언형 조건·결과·우선순위·결정표·상태 전이·게임 공식까지만 소유한다.
- [ ] `exception-spec`은 예외 조건·플레이어 피드백·보존 결과·보상·재시도·재진입 규칙까지만 소유한다.
- [ ] 위 네 kind에 `planning-authority-boundary.md`의 금지 구현 항목이 섞이지 않았다.

## 5. 플레이어 경험과 예외

- [ ] 선택 프로필이 영향을 주는 플레이어 과업과 목표 경험이 구체적이다.
- [ ] 시스템·화면·콘텐츠 피드백이 필요한 수준으로 설명된다.
- [ ] 실패, 취소, 재시도, 재접속, 저장·복구 중 관련 항목을 다룬다.
- [ ] 악용, 중복 보상, 잘못된 입력, 네트워크 오류 중 관련 위험을 검토한다.
- [ ] 접근성, 입력 대안, 현지화 확장성이 필요한 지점을 검토한다.
- [ ] 범위를 벗어난 상세는 해당 프로필 문서로 넘긴다.

## 6. 수치·경제·운영 조건부 점검

수치 또는 운영을 다루는 프로필에만 적용한다.

- [ ] 실제값, 목표값, 예시값, 추정값이 구분된다.
- [ ] 확률 합계와 상·하한이 모순되지 않는다.
- [ ] 공식의 계산 순서, 반올림, 캡, 예외가 정의된다.
- [ ] 핵심 자원의 소스와 싱크가 대응한다.
- [ ] 무한 생성, 교환 루프, 인플레이션, 중복 보상 경로를 검토한다.
- [ ] KPI가 플레이어 경험 또는 사업 의사결정과 연결된다.
- [ ] 분석 이벤트의 이름, 시점, 주요 속성이 정의된다.
- [ ] 운영 변경, 롤백, 알람과 담당이 필요한 항목을 식별한다.

## 7. 근거

- [ ] 최신 외부 사실에 직접 연결되는 출처가 있다.
- [ ] 출처에는 페이지 제목, URL, 확인일, 사용 목적이 있다.
- [ ] 사실, 해석, 설계 제안이 분리된다.
- [ ] 근거 없는 숫자는 가정 또는 예시값으로 표시된다.
- [ ] 충돌하는 자료는 채택 기준과 함께 기록된다.
- [ ] 외부 사실이 필요 없는 설계를 리서치 결과처럼 표현하지 않는다.

## 8. 시각화

- [ ] 다이어그램과 차트가 같은 내용을 장식적으로 반복하지 않는다.
- [ ] 프로필이 요구하는 Mermaid 최소 개수를 충족한다.
- [ ] `balance`는 근거 있는 Chart.js 수치 모델을 1개 이상 포함한다.
- [ ] 수치가 없는 프로필에 가짜 차트를 만들지 않았다.
- [ ] 차트에 단위, 데이터 성격, 캡션, 데이터 폴백 표가 있다.
- [ ] Mermaid 노드와 라벨이 읽히며 브라우저에서 오류 없이 렌더링된다.

## 9. HTML

- [ ] 독립적으로 열리는 단일 `.html` 파일이다.
- [ ] `gdd-profile` 메타데이터가 있고 선택 프로필과 일치한다.
- [ ] kind 문서에는 `gdd-kind` 메타데이터가 정확히 하나 있고 `document.kind`와 일치한다.
- [ ] 일반 profile 문서에는 존재하지 않는 kind를 나타내는 `gdd-kind`를 넣지 않았다.
- [ ] `gdd-scope-mode`, `gdd-sections`, `gdd-facets` 메타데이터가 입력 범위와 일치한다.
- [ ] 제목, viewport, 언어, h1이 있다.
- [ ] 표지와 브라우저 제목에서 한국어 문서 종류를 식별할 수 있다.
- [ ] 표지의 문서 종류 marker에 한국어 `<label>`이 한 번만 보이며 다른 표지 요소가 같은 문서명을 반복하지 않는다.
- [ ] `document.subtitle`에는 대상 기능과 목적만 보이며 canonical kind/profile ID는 표시되지 않는다.
- [ ] 모든 목차 링크가 실제 섹션 ID로 이동한다.
- [ ] ID가 중복되지 않는다.
- [ ] 템플릿 플레이스홀더와 렌더 오류 블록이 남아 있지 않다.
- [ ] 긴 표, 긴 URL, 긴 한국어 제목이 레이아웃을 깨지 않는다.
- [ ] 모바일에서 목차와 본문을 사용할 수 있다.
- [ ] 인쇄 시 사이드바·버튼이 숨겨지고 표가 읽힌다.
- [ ] `<project>_<kind>_GDD_<date>.html` 형식으로 같은 profile의 다른 kind를 덮어쓰지 않는다.

## 10. 프로필·kind 게이트

- [ ] 선택한 `profiles/<profile>.md`의 core section이 모두 있다.
- [ ] 패싯이 발동한 section과 그 dependency가 모두 있다.
- [ ] 선택되지 않은 canonical section을 관성적으로 추가하지 않았다.
- [ ] 선택된 각 canonical section의 최소 완료 조건을 충족한다.
- [ ] 프로필 파일의 기본 제외 항목이 본문에 섞이지 않았다.
- [ ] 프로필 파일의 Mermaid·Chart.js 조건을 충족한다.
- [ ] 추가 섹션은 사용자 목적에 필요한 `appendix-` 부록뿐이다.
- [ ] `appendix-kind-coverage` 또는 내부 생성·검토 과정을 설명하는 부록이 없다.
- [ ] kind가 있으면 해당 `references/kinds/<category>.md`의 질문, 필수 산출물, 기본 제외, 완료 조건을 충족한다.
- [ ] kind 계약의 기본 facet을 제거하거나 core/dependency와 충돌하는 제외가 없다.
- [ ] `production` 문서는 일정·담당·의존성·위험·QA·업데이트 중 kind가 요구하는 facet과 인수 조건을 충족한다.
- [ ] kind가 없는 일반 프로필 문서는 기존 프로필 게이트를 그대로 통과하며 kind 전용 게이트만 N/A다.

자동 검증 예:

```bash
python "$SKILL_DIR/scripts/validate_gdd.py" output.html \
  --profile ui-ux --kind ui-spec --require-scope
```

- [ ] `--kind` 값, `gdd-kind`, `document.kind`가 모두 같은 canonical ID다.
- [ ] 검증기가 kind/profile 매핑과 kind의 모든 `default_facets`를 통과로 보고한다.
- [ ] 일반 profile 경로에서는 `--kind`를 생략하고 `--profile ... --require-scope`로 검증했다.
