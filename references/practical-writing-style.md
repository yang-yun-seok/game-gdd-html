## 목표

회의, 구현 협의, QA 판정에 바로 쓰이는 문장만 남긴다. 생성 과정과 내부 분류 체계는 문서에 설명하지 않는다.

## 표지

- 한국어 문서명을 표지에서 한 번만 표시한다.
- 문서 종류의 canonical ID, profile ID, category, facet은 HTML 메타데이터에만 둔다.
- `document.subtitle`에는 대상 기능과 문서 목적만 쓴다.
- 프로젝트 브리프, 생성 방식, 범위 필터 결과를 표지에 넣지 않는다.

예:

```text
제작·강화 규칙과 실패 후 플레이어 상태를 정의한다
```

## 문장

- 짧은 선언형 문장을 쓴다.
- 한 문장에는 조건 또는 규칙 하나만 둔다.
- `한다`, `된다`, `표시한다`, `유지한다`, `지급하지 않는다`처럼 결과가 분명한 서술어를 쓴다.
- 결론과 규칙을 먼저 쓰고 이유는 결정에 필요한 만큼만 덧붙인다.
- 주어가 없으면 오해할 수 있는 문장에는 `플레이어`, `파티`, `아이템`, `화면`, `운영 담당자`를 명시한다.
- 같은 대상을 문서 전체에서 같은 용어로 부른다.

다음 표현은 최소화한다.

- `이 문서는`, `본 문서는`
- `제안한다`, `고려할 수 있다`, `권장된다`
- `요청을 분석한 결과`, `키워드를 조합하여`, `범위를 필터링했다`
- `다음과 같이 구성하였다`, `이 섹션에서는 살펴본다`
- 결론 없이 목적만 반복하는 장문 설명

## 내용 순서

필요한 항목만 다음 순서로 작성한다.

1. 적용 조건과 대상
2. 규칙과 우선순위
3. 플레이어가 확인할 결과
4. 실패·취소·재진입 예외
5. 화면 표시와 조작 피드백
6. 수치·데이터의 논리 의미
7. 검증 조건과 미정 사항

섹션 첫 문단은 배경 설명보다 결정 사항을 먼저 쓴다. 표는 비교, 상태, 조건 분기에만 사용한다.

## 규칙 작성

규칙은 가능한 한 다음 열로 정리한다.

| 항목 | 작성 내용 |
|---|---|
| 조건 | 규칙이 적용되는 상태와 선행 조건 |
| 입력 | 플레이어 선택 또는 게임 내 사건 |
| 규칙 | 게임이 판정해야 할 내용 |
| 결과 | 플레이어가 확인하는 상태·보상·피드백 |
| 예외 | 실패, 취소, 중복, 재진입 처리 |
| 검증 | QA가 재현하고 판정할 기준 |

구현 순서, 저장 방식, 통신 방식은 적지 않는다.

## 표현과 라벨

- 표 제목, 카드 제목, 태그, 담당명은 한국어를 우선한다.
- `PILLAR 01`, `DESIGN`, `OWNED`, `REFERENCE`, `HANDOFF` 같은 내부·장식용 영문 대문자 표기를 만들지 않는다.
- 제품명, 장르의 통용 약어, 공식 지표명처럼 필요한 영문만 사용한다.
- `확정`, `가정`, `검토 필요`를 구분한다. `TBD` 대신 `검토 필요`를 우선한다.
- 근거 없는 수치에는 `예시값` 또는 `가정값`을 붙인다.

## 기획과 개발의 경계

권한 경계 설명을 표지와 각 섹션에 반복하지 않는다. 구현 판단이 실제로 필요한 항목만 `개발 협의`로 모은다.

`개발 협의`에는 다음만 쓴다.

- 기획 요구
- 플레이어가 확인할 결과
- 측정 가능한 품질조건
- 알려진 제약
- 결정 담당과 시점

구현 해법은 선택하지 않는다.

## 내부 정보 비노출

다음 정보는 생성·검토용 JSON과 내부 점검에만 둔다.

- GDDQL
- profile·kind·category의 canonical ID
- facet, scope, selected section
- required output, coverage 상태
- `owned`, `reference`, `N/A`
- handoff 계약과 내부 라우팅 근거

본문, 표지, 목차, 부록, 결정 로그에 위 용어와 값을 설명하지 않는다. 다른 문서와 실제 협업 내용을 사용자가 요청한 경우에만 독자 친화적인 한국어 협업 표를 만든다. 이때도 canonical 코드 대신 문서명, 필요한 결정, 전달 자료, 완료 기준, 담당을 쓴다.

## 전환 예

나쁜 예:

```text
본 문서는 캐릭터 시스템 전반을 정의하며, 분석된 패싯을 기반으로 성장 방향을 제안한다.
```

좋은 예:

```text
캐릭터는 원정 종료 후 획득한 경험치로 성장한다. 원정 중에는 레벨이 오르지 않는다.
```

나쁜 예:

```text
중복 보상 방지를 위해 멱등 처리 방식의 적용을 고려할 수 있다.
```

좋은 예:

```text
같은 완료 결과로 보상을 두 번 지급하지 않는다. 반복 입력과 재접속에서도 최종 보상 수량은 같다.
```

## 최종 점검

- 첫 화면에서 한국어 문서 종류가 한 번만 보이는가
- subtitle이 문서 목적만 설명하는가
- 내부 생성 과정과 canonical 코드가 보이지 않는가
- 각 규칙에 조건, 결과, 예외, 검증 기준이 있는가
- 설명보다 결정 사항이 먼저 나오는가
- 구현 방식 대신 품질조건과 개발 협의만 남았는가
