# UI·UX 기획서 kind

흐름, 화면 명세, 와이어프레임, 입력 장치를 분리한다. UI 문서는 시스템의 결과를 표현하지만 계산·지급·상태 판정 자체를 소유하지 않는다.

| 기획서 / kind ID / profile | 목적·주 독자 | 반드시 답할 결정 | 필수 산출물 | 기본 제외 | 인접 문서 핸드오프 | 완료 조건 |
|---|---|---|---|---|---|---|
| UI 기획서<br>`ui-spec`<span id="ui-spec"></span><br>`ui-ux` | 화면·메뉴·컴포넌트와 상태 표현 정의<br>UI 디자이너, 클라이언트, 시스템·QA 기획자 | 어떤 화면에 어떤 정보·행동이 있으며 정상·로딩·빈값·잠금·오류 상태를 어떻게 표현하는가? | 화면·메뉴 지도, 화면별 요소·동작 표, 팝업·내비게이션, 상태·검증·피드백, 반응형 요구 | 게임 규칙·수치 계산, 최종 비주얼 아트, 입력 장치 충돌 정책 | 입력: `ux-flow`, 대상 시스템 kind<br>출력: `wireframe`, `data-table-spec`, `exception-spec` | 모든 요소가 데이터 원천·행동 결과·상태·시스템 계약으로 추적된다 |
| UX 흐름도<br>`ux-flow`<span id="ux-flow"></span><br>`ui-ux` | 사용자 목표 달성 경로와 이탈·복구 설계<br>UX·UI·시스템·QA 기획자 | 진입점부터 완료까지 어떤 행동·분기·대기·실패·취소·복구를 거치는가? | 목표별 플로차트, 진입·종료점, 결정·시스템 응답, 예외·복귀 경로, 완료 측정 지점 | 픽셀 배치, 최종 카피, 내부 계산·데이터 스키마 | 입력: 대상 시스템 kind, `game-concept`<br>출력: `ui-spec`, `wireframe`, `logging-spec`, `tutorial-design` | 주 경로와 모든 고위험 분기가 끊김 없이 화면·시스템 상태에 연결된다 |
| 와이어프레임<br>`wireframe`<span id="wireframe"></span><br>`ui-ux` | 그래픽 제작 전 정보 위계·배치 검증<br>UX·UI·아트·개발 협업 담당 | 핵심 정보와 행동을 어떤 위계·영역·크기로 배치하며 화면 크기별로 어떻게 변하는가? | 주석형 프레임, 컴포넌트 목록, 인터랙션 핫스폿, 전환 연결, 해상도·방향 변형 | 최종 색·타이포·일러스트, 시스템 로직, 오류 보장 방식 | 입력: `ui-spec`, `ux-flow`<br>출력: `ui-spec` 화면 주석, UI 아트 작업, 개발 협의 항목 | 주요 상태·분기·해상도 프레임이 있고 모든 인터랙션이 목적지 또는 결과를 가진다 |
| 조작 기획서<br>`control-scheme`<span id="control-scheme"></span><br>`ui-ux` | 키보드·마우스·패드·터치 입력 계약 정의<br>전투·UX·접근성·QA 기획 및 개발 협업 담당 | 행동을 어떤 입력에 매핑하며 문맥·우선순위·동시 입력·재설정·장치 전환을 어떻게 처리하는가? | 액션 맵, 문맥 레이어, 탭·홀드·연타·조합 규칙, 충돌 우선순위, 리맵·접근성·햅틱 요구 | 전투 결과 판정, 화면 배치, 플랫폼 입력 구현 상세 | 입력: `character-combat`, `ui-spec`<br>출력: `tutorial-design`, `exception-spec`, 입력 품질조건과 개발 협의 항목 | 지원 장치마다 모든 필수 행동에 도달 가능하고 입력 충돌·전환·접근성 대안이 검증된다 |
